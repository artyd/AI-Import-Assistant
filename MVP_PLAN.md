# MVP «Штурман» для декларанта — план реализации

> Источник этого плана — структурированный разбор (grilling) от 2026-09-10 + аудит
> текущего кода + разбор реальной эталонной поставки «Метопрен». Все решения ниже
> **зафиксированы и подтверждены**. Это рабочий план, а не черновик обсуждения.

---

## 0. Одна фраза

Превращаем «песочницу, которая раскидывает файлы по папкам» в **ассистента
декларанта**, который по одной поставке говорит: *чего не хватает* и *где инвойс не
бьётся с упаковочным* — надёжно, с цитатами-источниками, до подачи на таможню.

**Корневой вывод:** три боли (раскладка / контекст / «не видит проблем») — это один
сбой в одной точке — **качество и доверие к извлечению полей** (`document_extractions`).
Всё остальное (чек-лист, сверка, риски, раскладка) — чистые функции над этой таблицей.
Чиним извлечение первым; остальное встаёт сверху.

---

## 1. Границы MVP

### Пользователь и сценарий
- **Пользователь №0:** декларант. Пилот стартует **один** (multi-user — потом).
- **Workflow №1:** одна поставка → ручная загрузка пакета → экран с чек-листом
  полноты и ранжированными флагами расхождений → декларант правит → ZIP-экспорт для
  архива. Всё до таможни.

### Критерий готовности («не песочница»)
1. Продукт **заменил ручной шаг** сверки инвойс↔упаковочный.
2. **Ни разу не соврал** на золотом наборе (не выдумал расхождение, не пропустил
   настоящее) — измеримо, см. Фаза 0.
3. Пилот провёл **5–10 реальных поставок** и подтвердил экономию времени.

### В scope MVP-среза 1
- Ручная загрузка файлов.
- Извлечение по **коммерческому набору**: инвойс, упаковочный, контракт, PO, CoO,
  сертификат качества.
- Человек в контуре: экран проверки вычитанных полей.
- Сверка итогов + полей, ранжированные флаги (🔴 с двумя цитатами / 🟡 сомнение).
- Дашборд поставки (структурный UI), чат — помощник сбоку.
- ZIP-экспорт с папочной структурой.

### Осознанно ЗА бортом
- **Убрано вовсе (ближайшее время):** письма поставщику
  (`generate_supplier_instruction`), автоприём с почты/диска/1С, многопользовательские
  роли и handoff.
- **Быстрый след (после «да» от пилота):** HTML-отчёт (`generate_report`); уведомления
  в порядке `нехватка документов → дедлайны → сроки сертификатов` (последнее ждёт
  надёжного OCR).
- **Отдельные фазы:** список всех поставок для менеджера ВЭД (другой пользователь);
  подбор УКТ ЗЕД + справочная база ТН ВЭД (**Phase 6**); извлечение транспорт/таможня
  (CMR/AWB/МД); полная построчная сверка позиций; семантический дедуп дубликатов.

## 2. Что показал эталон «Метопрен» (почему план именно такой)

| Находка | Следствие для плана |
|---|---|
| Инвойс + упаковочный **в одном файле** (2-в-1) | Сверка обязана уметь брать оба извлечения из одного файла. Текущая логика берёт отдельный файл на тип — сломается. |
| Один документ в 3 формах (PDF / `.doc` / скан) | `content_hash` их не поймает (не байт-идентичны). В MVP — подсказка «возможно дубль», выбор человека. |
| Поставка **однопозиционная** (1 строка) | Полная таблица line-items в MVP не нужна. Сверяем итоги + позиции как поля. Многопозиционные — честная деградация. |
| УКТ ЗЕД **только в декларации**, не в инвойсе | В MVP код почти нечего сверять → сверка согласованности, подбора нет. |
| Половина документов — **сканы**, 3 языка | OCR — первоклассный риск. Нечитаемый скан → честный статус + ручной ввод полей. |
| Целый пласт транспорт/таможня не смоделирован | Вне MVP (Q23). Отдельная фаза. |

## 3. Порядок работ

### Фаза 0 — Эталон / золотой набор (ДО кода)
**Цель:** объективный руль качества. Без него «не соврал» непроверяемо.

- [ ] Пилот-декларант размечает **5–10 реальных прошлых поставок** (обяз. смесь:
      одно-/многопозиционные, цифровые/сканы, дву-/трёхсторонние; «Метопрен» — первая).
- [ ] Для каждой: верные ключевые поля по каждому документу + список реальных
      расхождений (что есть / чего быть не должно).
- [ ] Формат хранения золотого набора + прогонщик, ложится на существующий механизм
      `npm run eval:*` (см. `package.json`, паттерн `eval:grounding`).
- [ ] Метрики: точность извлечения по полю, доля пойманных реальных расхождений
      (recall), доля ложных тревог (precision).

**Приёмка фазы:** прогон эталона запускается одной командой и выдаёт цифры.

---

### Фаза 1 — Доверие к извлечению (корневой рычаг)
**Файлы:** `src/services/extraction/extractFields.ts`, `src/services/extract/index.ts`,
`src/services/ocr/claudeOcr.ts`, `src/worker/index.ts`, `src/db/schema.sql`.

- [ ] **Гибридная схема извлечения** (Q30-C): общий костяк (номера/даты/стороны/суммы)
      + прицельные поля для инвойса и упаковочного (нетто/брутто/места/позиции).
      Сейчас одна плоская схема на всё (`extractFields.ts:55-75`) — расширить/ветвить по
      `doc_type`.
- [ ] **Оценка уверенности по каждому полю.** Сейчас её нет. Добавить в извлечение
      и в `document_extractions.extracted_fields` (`schema.sql:129`).
- [ ] **Обработка 2-в-1** (инвойс+упаковочный в одном файле): одно извлечение может
      порождать роли обоих типов для последующей сверки.
- [ ] **Честный статус нечитаемого скана** (Q29-A): если OCR/vision не дал надёжного
      результата — статус «не смог прочитать», без молчаливого выпадения из сверки.
      Усилить vision-first путь и fallback (`extractFields.ts:238-259`, `claudeOcr.ts`).
- [ ] **Экран проверки полей** (Q17-C через B): пакетный экран — вычитанные поля рядом
      с документом; обязательное подтверждение только для спорных+важных (низкая
      уверенность или влияет на вердикт), остальное редактируемо, но принимается молча.
      Нужен REST-роут + FE-экран; правки пишутся обратно в `document_extractions`.

**Приёмка фазы:** на золотом наборе точность извлечения ключевых полей достигает
целевого порога; ни один документ не выпадает из анализа молча.

---

### Фаза 2 — Сверка и флаги («видит проблемы»)
**Файлы:** `src/services/discrepancies.ts`, `src/services/risks.ts`,
`src/services/checklist.ts`.

- [ ] **Сверка итогов + полей** инвойс↔упаковочный↔контракт: кол-во мест, вес
      (нетто/брутто), сумма, номера. Расширить текущую `computeDiscrepancies`
      (`discrepancies.ts`) — сейчас 3 типа и только итоги.
- [ ] **Несовпадение валюты** — сейчас молча пропускается (`discrepancies.ts:99`).
      Сделать явным флагом.
- [ ] **Сверка сторон** (продавец/покупатель/получатель) между документами и с
      заявленными `parties` (`schema.sql:115`). Сейчас нет вовсе.
- [ ] **Инкотермс, страна происхождения, наличие CoO** — как ранжированные флаги.
- [ ] **Ранжированные флаги** (Q15-C): 🔴 = детерминированное расхождение с **двумя
      цитатами-источниками** (обязательно!); 🟡 = сомнение / поле не прочиталось.
- [ ] **Деградация на многопозиционных** (Q26-A): сверяем итоги + честно «построчно не
      проверял». Никогда не притворяемся, что проверили.
- [ ] **УКТ ЗЕД** — только сверка согласованности, когда код присутствует (Q24-A).
- [ ] **Чек-лист полноты** привязать к коммерческому набору (`checklist.ts` + шаблоны
      `checklist_templates`, `schema.sql:197-227`).

**Приёмка фазы:** на золотом наборе recall реальных расхождений и precision (мало
ложных тревог) достигают целевых порогов; каждый 🔴 несёт две цитаты.

---

### Фаза 3 — Экран декларанта (дашборд-first)
**Файлы:** FE (`frontend/`) + существующие роуты `src/routes/` (checklist,
discrepancies), новые роуты для проверки полей и экспорта.

- [ ] **Дашборд поставки:** список документов с ярлыками типа + подсказки «возможно
      дубль» + флаг «файл из чужой поставки» (Q22-B); чек-лист полноты; список флагов
      🔴/🟡 с раскрытием цитат; кнопка «проверить поля».
- [ ] **Чат — помощник сбоку** (объяснения флагов, вопросы). Единый агент сохраняется:
      дашборд читает те же детерминированные данные (хард-констрейнт не нарушается).
- [ ] **ZIP-экспорт** (Q16-A): папочная структура (`01_...`, `02_...` из
      `domain/folders.ts`) собирается **в момент экспорта** из подтверждённого человеком
      типа документа. Никакого авто-перемещения при загрузке.
- [ ] **Демонтаж молчаливой авто-раскладки** при загрузке (`classify.ts`,
      `worker/index.ts:164-184`): тип определяем и показываем как ярлык/подсказку,
      перемещение файлов — решение человека либо только на экспорте.

**Приёмка фазы:** декларант проводит поставку из эталона от загрузки до ZIP целиком
через экран; видит проблемы за секунды.

---

## 4. Быстрый след (после «да» от пилота)
- HTML-отчёт по поставке (`generate_report`) — для передачи/архива.
- Уведомления: сначала нехватка документов (данные из чек-листа, надёжно), затем
  дедлайны, затем сроки сертификатов (после того как OCR сертификатов докажет
  надёжность).
- Полная построчная таблица line-items — когда многопозиционные поставки участятся.

## 5. Отдельные фазы (не в очереди MVP)
- Список всех поставок для менеджера ВЭД (другой пользователь, роли/handoff).
- Подбор УКТ ЗЕД + справочная база ТН ВЭД / официальные источники — **Phase 6**.
- Извлечение транспорт/таможня (CMR, AWB, MRN, декларация) + сверка «МД vs инвойс».
- Автоприём документов (почта/диск/1С).
- Семантический дедуп дубликатов в разных форматах.

---

## 6. Сквозные принципы (не нарушать)
1. **Не притворяться, что проверил то, что не проверял.** Нечитаемо / не хватает данных
   / многопозиционно — говорим честно, а не молчим.
2. **Каждый 🔴 красный флаг = две цитаты-источника.** Иначе это мнение, а не факт.
3. **Всё меряется золотым набором** после каждого изменения ядра.
4. Хард-констрейнты из `CLAUDE.md` в силе: один агент, гибридное извлечение, ключи
   только на сервере, модель `claude-opus-4-8`.
