# ТЗ: Штурман читає кожен файл повністю і лише потім розкладає

Status: in-progress (тікети 1–6 реалізовані 2026-10-28; чекають деплою й приймання на реальному збірнику)

Сьогодні файл читається у фоні, кладеться в папку одразу після власного читання
(до того, як прочитано інші файли пачки), а користувач не бачить, що відбувається.
У збірнику папки плоскі («Партія — X»), поняття «товар» немає. Документи читає
Sonnet 5.5 з effort `low`.

Рішення погоджено з замовником 2026-10-28.

## Погоджені рішення

| Питання | Рішення |
|---|---|
| Модель читання | **Claude Haiku 5.5** (`claude-haiku-5-5`) для всього аналізу файлів: розпізнавання (vision), витяг полів, класифікація. Чат Штурмана — як і раніше `ANTHROPIC_MODEL` |
| Якість читання | Кожна сторінка кожного файлу — повністю, до дрібниць (печатки, штампи, етикетки, штрихкоди, рукописне, дрібний шрифт). effort `medium`. Сторінка, що не прочиталась, перечитується поодинці; текстовий шар — лише запасний варіант |
| Структура збірника | `Партія — Постачальник/Товар/` (усе по товару) + `Партія — Постачальник/Інше/` (товар не визначено); `Митниця/Постачальник/` (інвойси, PL, контракт, маркування, CoO) + `Митниця/Весь контейнер/` (МД, наш перепродаж, маніфест); `Транспорт/`. **Папки «Маніфест» немає; файлів поза папками немає** (нерозкладені — у папці «Інбокс — не розкладені»; zip не створює власних папок, порожні «чужі» папки прибираються) |
| Документ на кілька товарів | Файл один, а **посилання** на нього — у папці кожного товару, якого він стосується |
| Коли розкладати | **Після** того, як прочитано всю пачку: спершу якірні документи (інвойс/PL/контракт — створюють постачальників і товари), потім решта |
| Прогрес | Живий потік «читаю / прочитав / кладу в…» **у чаті і в Журналі**; журнал зберігається в БД |
| Папка на сервері | Кожне постачання/збірник має людську теку на диску сервера, що дзеркалить дерево (жорсткі посилання, без копій байтів) |

## Модель даних

- `folders.parent_id` (вкладені папки), `folders.role`
  (`lot` | `lot_customs` | `product` | NULL для кореневих), `folders.product_key`.
- Папка постачальника: `lot_id = L`, `parent_id NULL`, `role='lot'`.
- Папка товару: `lot_id = L`, `parent_id` = папка постачальника, `role='product'`.
- Митниця постачальника: `lot_id = L`, `parent_id` = `Митниця`, `role='lot_customs'`.
- Партія файлу = `lot_id` його папки (як і раніше) — тому всі три види папок
  належать партії, і вердикти партії не змінюються.
- `file_links (file_id, folder_id)` — додаткові місця файлу (папки товарів).
  Вердикти рахують файл один раз — за його основною папкою.
- `ingest_events` — журнал читання/розкладання (workspace, file, batch, kind, text).

## Розкладання (детерміновано, після читання пачки)

1. Маніфест → `Маніфест`; транспорт (MBL/HBL/T1/CMR/AWB) → `Транспорт`; МД → `Митниця`.
2. Партія — за правилами spec 006 (`assignLot`).
3. У партії: інвойс / PL / контракт / CoO / маркування / інструкція → `Митниця/<постачальник>`;
   CoA, MSDS, специфікації, реєстраційні, фото та інше по товару → `<постачальник>/<товар>`.
4. Товари партії створюються з якірних документів (рядки інвойсу/PL/контракту:
   коротка назва + CAS). Супровідні документи товарів не створюють.
5. Документ, що називає товари, отримує посилання в папку кожного з них.
6. Неоднозначне — в Інбокс з підказкою (як і раніше).

## Прогрес

Подія SSE `ingest_log` на каналі `/events` + `GET /api/workspaces/:id/ingest-log`.
Рядки: «Читаю …», «… стор. 6–10 з 20», «Прочитано: інвойс від A, 3 товари»,
«Кладу → Митниця / A (+ товари: …)», підсумок пачки.

## Тікети

1. Моделі → Haiku 5.5, промпт розпізнавання «до дрібниць», effort `medium`.
2. Схема: вкладені папки, `file_links`, `ingest_events`; витяг: товар і CAS у рядках.
3. Розкладання збірника після пачки + папки товарів + посилання.
4. Журнал читання: запис, SSE, API, Журнал і картка в чаті.
5. Дерево файлів з вкладеністю і посиланнями.
6. Дзеркало на диску сервера; ZIP за новою структурою.
