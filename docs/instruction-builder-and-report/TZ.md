# ТЗ: Конструктор інструкцій постачальнику + Звіт для керівництва

Блок **Комплектність → Дії** у поставці. Дві кнопки, які зараз працюють слабко:

- **«Інструкція»** — модалка з 5 галочками. Claude пише лист українською з нуля:
  щоразу витрачає токени, результат щоразу інший, а дані документів не використовуються.
- **«Експорт звіту (HTML)»** — технічна HTML-сторінка з таблицями
  (`src/services/report.ts`, без LLM). PDF немає, вигляд не для керівництва.

Рішення погоджено з замовником 2026-10-05 (сесія питань-відповідей). Зразок
конструктора — `конструктор_інструкцій_поставки.html` (9 блоків форми, живе
прев'ю англійського листа, пресети, посилання на qdpro). Будуємо **покращену
інтегровану** версію.

Тестова поставка для приймання — **«TEST-Метопрен v2»** (S-methoprene, NGL India →
PRIME FORCE UK → ТОВ «ТЕХІНФОРМ ПЛЮС», авіа + авто, вже розмитнена).

## Частина 1. Конструктор інструкцій постачальнику

### 1.1 Погоджені рішення

| Питання | Рішення |
|---|---|
| UX | **Окремий повноекранний конструктор** з живим прев'ю **+ Штурман**. Штурман може відкрити конструктор із чату й допомогти з порожніми полями |
| Мова листа | **Англійська** (лист постачальнику) + **українське прев'ю** для внутрішньої перевірки |
| Генерація тексту | **Детермінований шаблон** (0 токенів, завжди однаковий) + опційна кнопка «Доопрацювати з ШІ» для нестандартних вимог |
| Автозаповнення | Сторони й контракт · товар із документів · документи й дозволи за кодом із **qdpro** · збережені шаблони |
| Коли складається | **До відвантаження, за контрактом.** Джерела: контракт/специфікація/замовлення, картка сторін, попередні поставки того ж постачальника. Решту вводить користувач |
| Вивід | Копіювати текст · **DOCX** · **PDF** · e-mail (`mailto:` з адресою постачальника; SMTP — окремий етап) |
| Після відправки | Інструкцію **зберігаємо структурно** і **автоматично звіряємо** з документами, що надійшли (без токенів) |
| Шаблони | **Спільні для всієї команди** |
| Від чийого імені | **Вибір із довідника** компаній групи (реквізити, підписант). За замовчуванням — покупець зі сторін поставки |
| Стиль PDF | Дизайн-система Штурмана |

### 1.2 Екран конструктора

Маршрут `/workspaces/[id]/instruction`. Відкривається кнопкою «Інструкція» в «Діях»
або дією Штурмана. Ліворуч форма, праворуч прев'ю з перемикачем **EN / UK**.

Розділи форми (на базі зразка, покращено):

1. **Від імені** — компанія групи з довідника (реквізити, підписант, e-mail).
2. **Категорія товару** — субстанція (АФІ) / готовий препарат / хімія / харчова / інше.
   За замовчуванням «субстанція» (портрет користувача). Від категорії залежать
   типові документи й поля маркування.
3. **Товар і код** — назва, ґатунок, CAS, кількість + одиниця, код УКТ ЗЕД,
   реєстраційний номер МОЗ / ветпрепарату (якщо є).
4. **Відправник (Consignor)** — шаблон із довідника або нова компанія.
5. **Одержувач (Consignee)** і кінцевий вантажоодержувач. Для тристоронньої схеми
   подсвічується, хто є consignee (на Метопрені інструкція вимагала PRIME FORCE,
   а у фактичних документах — ТЕХІНФОРМ; тут це рішення фіксується явно).
6. **Контракт** — номер і дата (з витягу контракту).
7. **Умови поставки** — Incoterms (код) + місце; аеропорт/порт відвантаження й
   призначення; кінцевий пункт; вид транспорту (sea / air / road / multimodal).
8. **Пакет документів** — чек-лист:
   - базовий набір від категорії;
   - **плюс документи й дозволи за кодом із qdpro** (`uktzed_lookup_code`, режим
     ІМПОРТ): ветеринарні/фітосанітарні, 5509, 5520 тощо, з поміткою «джерело: qdpro»;
   - страховий поліс за CIF/CIP;
   - копія експортної декларації.
9. **Маркування** — поля етикетки (чекбокси від категорії) + примітки; реєстраційний
   номер друкується на етикетці.
10. **Чернетки на погодження** — що надіслати до відвантаження (етикетка, інвойс/PL,
    COO, транспортний документ, фото) і заборона випускати оригінали без погодження.
11. **Оригінали кур'єром** — контакт, телефон, адреса (шаблон із довідника).

Поведінка:

- Кожне поле показує **джерело автозаповнення** (бейдж «з контракту
  03062026PTM.pdf», «з qdpro», «шаблон», «вручну»). Незаповнені обов'язкові поля
  підсвічені, а лічильник «⚠ N полів не заповнено» блокує експорт.
- **«Спитати Штурмана»** відкриває чат із контекстом конструктора. Агент
  отримує інструмент `instruction_draft` (читати/оновлювати поля конструктора) і
  може запропонувати значення з документів (наприклад, «у контракті вказано FCA
  Mumbai — підставити?»), але **не зберігає без підтвердження**.
- **«Доопрацювати з ШІ»** (опційно): Claude отримує готовий шаблонний лист +
  вільний запит («додай вимогу про температурний режим») і повертає правку, яку
  показуємо як diff. Прийняти правку чи ні — вирішує користувач.
- Зберігається як **версії** (v1, v2…) з датою й автором. Останню затверджену
  версію використовує автоперевірка.

### 1.3 Генерація листа

- Шаблон — чиста TS-функція `renderInstruction(draft, lang)`
  (`src/services/instruction/render.ts`) → текст/Markdown. EN — лист постачальнику,
  UK — та сама структура українською. Тексти фраз — у словнику, не в коді.
- **DOCX** — бібліотека `docx` (Node). **PDF** — HTML-шаблон у стилі Штурмана →
  headless Chromium (спільний рендерер із Частиною 2).
- **E-mail** — `mailto:` з темою «Shipping instructions — <товар> / <контракт>»,
  тілом EN-листа й адресою постачальника з довідника.

### 1.4 Автоперевірка виконання інструкції

Затверджена інструкція — це структура `{consignee, consignor, incoterm, place,
final_destination, transport_mode, required_docs[], label_fields[], originals[]}`.
Детермінований модуль `instructionCompliance.ts` звіряє її з
`document_extractions` і повертає пункти:

- `consignee_mismatch` — consignee у AWB/COO/PL ≠ інструкції (Метопрен: ТЕХІНФОРМ ≠ PRIME);
- `incoterm_mismatch`, `destination_mismatch` (Kharkiv ≠ Kyiv);
- `required_doc_missing` — страховий поліс, експортна декларація;
- `label_field_missing` — поле етикетки не знайдено.

Результат з'являється в «Розбіжностях» (поле `instruction`) і в ризиках. Агент
бачить його через `get_discrepancies`, без окремих токенів.

### 1.5 Дані (схема)

- `org_directory` — спільний довідник: `id, kind (own_company|supplier|consignee|contact),
  name, address, country, requisites jsonb, signer, email, phone, created_by, updated_at`.
- `supplier_instructions` — `id, workspace_id, version, status (draft|approved|sent),
  lang, draft jsonb (усі поля + джерела), rendered_en, rendered_uk, created_by, created_at`.
- Наявний `generated_artifacts` лишається для експортованих файлів (DOCX/PDF).

### 1.6 API (нове)

- `GET  /api/workspaces/:id/instruction/prefill` → чернетка з автозаповненням і джерелами по кожному полю (без LLM; qdpro — якщо `LOGIST_MCP_URL`).
- `GET/POST /api/workspaces/:id/instructions` · `GET/PATCH /api/workspaces/:id/instructions/:ver` (зберегти, затвердити).
- `GET  /api/workspaces/:id/instructions/:ver/render?lang=en|uk&format=txt|docx|pdf`.
- `POST /api/workspaces/:id/instructions/:ver/refine` `{ request }` → запропонована правка (LLM, опційно).
- `GET/POST/PATCH/DELETE /api/directory` — спільний довідник.
- Наявний `POST /supplier-instruction` залишаємо як deprecated alias (повертає шаблонний EN-лист), щоб не зламати старий фронтенд.

## Частина 2. Звіт для керівництва

### 2.1 Погоджені рішення

| Питання | Рішення |
|---|---|
| Обсяг | **Рівно 1 сторінка A4** — щільний дашборд із компактних карток; деталі не влазять → «детально в Штурмані» |
| Блоки | Стандартні (сторони, комплектність, розбіжності, ризики) **+ фінанси й платежі, таймлайн, маршрут, товар і класифікація** |
| Збірка | Дані — **кодом без LLM** (як зараз); верстка — HTML у стилі Штурмана; **PDF — headless Chromium у бекенді** (TypeScript, один стек). Python не потрібен: токенів не витрачаємо в обох варіантах |
| ШІ-резюме | **Коротке (3–5 речень) дешевою моделлю** (Sonnet) за вже порахованими фактами; кешується, перераховується лише при зміні даних |
| Формати | PDF (основний) + HTML |
| Стиль | Дизайн-система Штурмана (Hanken Grotesk, `--accent #2F6FEB`, лого ШТУРМАН), друк на світлій темі |

### 2.3 Дані для блоків (усі детерміновані)

- **Фінанси:**
  - вартість по плечах (вхідний/вихідний інвойс) і націнка;
  - з МД: митна вартість, мито, ПДВ, курс НБУ;
  - з рахунків за послуги (фрахт DSV, брокер): сума витрат;
  - **собівартість за кг**: вартість + платежі + послуги.
  - Для цього потрібне витягування з МД і сервісних рахунків (див. 2.5).
- **Таймлайн** — дати з документів (`document_date`, `shipment_date`), упорядковані за
  етапами; тривалість «контракт → МД» і по етапах.
- **Маршрут** — точки з AWB/CMR/T1 (аеропорти, митниці, кінцевий пункт) + вид
  транспорту на кожному плечі.
- **Товар і класифікація** — назва, CAS, партія, дати виробництва/придатності (COA),
  код УКТ ЗЕД + ставки з qdpro (якщо доступний, інакше з МД — з позначкою джерела).
- **Сторони, комплектність, розбіжності, ризики** — з наявних сервісів (у звіт
  потрапляють лише лічильники + топ-3 ризики).
- **ШІ-резюме** — один виклик Sonnet: на вхід JSON фактів звіту (без документів),
  на вихід 3–5 речень українською, нейтрально. Кешується за хешем фактів.

### 2.4 Технічно

- `src/services/report/` — `collectFacts(ws)` (чиста збірка фактів) →
  `renderReportHtml(facts)` (шаблон) → `renderPdf(html)` (Chromium).
- **PDF-рендерер** спільний з інструкцією. Chromium у Docker-образі бекенду
  (`playwright-core` + системний `chromium` у `node:20-slim`, або окремий легкий
  сервіс `gotenberg`; вибір — на етапі реалізації, критерій — розмір образу й
  стабільність).
- `POST /api/workspaces/:id/report` → `{ artifactId, html }` (як зараз) +
  `GET /api/workspaces/:id/report/:artifactId.pdf`. Кнопка «Експорт звіту» →
  меню **PDF / HTML**.
- Сторінка гарантовано вміщається в 1 A4: тексти обрізаються з «…», а списки
  обмежено (топ-3).

### 2.5 Залежності від витягування

Для фінансового блоку та таймлайну потрібні поля, яких зараз немає в схемі витягування:

- МД: `customs_value_uah`, `duty_uah`, `vat_uah`, `exchange_rate`, `declaration_date`;
- рахунки за послуги (`doc_type=other` з підтипом `service_invoice`): `service_kind`
  (freight / broker / storage), `amount`, `currency`.

Розширюємо `record_extraction` опційними полями. Старі файли отримують ці поля
після `reindex`.

## Етапи

1. **Макети на погодження** — HTML-макети конструктора й звіту на даних Метопрена
   (без бекенду).
2. **Звіт:** витягування МД/рахунків → `collectFacts` → HTML → PDF → кнопка PDF/HTML → ШІ-резюме.
3. **Конструктор:** довідник → prefill API → екран + шаблон EN/UK → DOCX/PDF/mailto → версії.
4. **Штурман у конструкторі:** інструмент `instruction_draft`, «Спитати Штурмана», «Доопрацювати з ШІ».
5. **Автоперевірка інструкції** в розбіжностях і ризиках.

## Критерії приймання (на «TEST-Метопрен v2»)

- **Звіт** — 1 сторінка A4 PDF; цифри збігаються з еталоном:
  - 8 750 / 13 125 USD;
  - мито 25 418,35 ₴, ПДВ 83 293,97 ₴, курс 44,6916;
  - маршрут Mumbai → Frankfurt → Київ → Біла Церква;
  - топ-ризики: КМВ, T1 нетто, брутто.

  Генерація без ШІ — ≤ 3 с, з резюме — ≤ 10 с.
- **Конструктор:**
  - prefill підставляє NGL / PRIME / ТЕХІНФОРМ, контракт 03062026/PTM,
    S-METHOPRENE 25 кг, 2918999090, CPT/FCA по плечах, авіа + авто;
  - qdpro додає документи 5509/5520;
  - EN-лист без жодного виклику LLM;
  - DOCX і PDF відкриваються.
- **Автоперевірка:** інструкція з consignee = PRIME FORCE і страховим полісом на
  Метопрені дає `consignee_mismatch` і `required_doc_missing` (страховий поліс,
  експортна декларація).
